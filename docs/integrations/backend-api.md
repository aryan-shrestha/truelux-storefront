## About this document

This is a transcription of the contract published by the **backend repository**
(`clothing-store/backend`), so that storefront code is written against a fixed
document rather than a recollection of one.

**The backend repository is authoritative.** If this file and `backend/docs/`
disagree, the backend is right and this file is stale. Fix it here; do not work
around it in `lib/api`.

This document records **what the API does**. It does not record what the storefront
does about it — that is the job of [ADR 0001](../decisions/0001-the-browser-makes-every-customer-scoped-call.md),
[ADR 0005](../decisions/0005-the-storefront-branches-on-api-error-codes.md) and
the feature documents. Keeping the two separate is what stops this file drifting
into a design document.

Transcribed from, and verified against:

## Base URL and versioning

```text
{API_BASE_URL}/api/v1/...
```

Local development: `http://localhost:8000/api/v1/`.

`v1` is both a path prefix and a DRF namespace. `ALLOWED_VERSIONS` is `("v1",)` —
there is no other version, and `/api/v1/` responses are promised to stay backward
compatible. A breaking change would arrive as `/api/v2/`.

Every route ends in a **trailing slash**. Django will redirect a request without
one, which costs a round trip and turns a `POST` into a `GET` on some clients.
Always send the slash.

There is no API-root document at `/api/v1/` — the backend registers a
`SimpleRouter`, not a `DefaultRouter`, deliberately. Do not probe for one.

An OpenAPI 3 schema is served at `/api/schema/`, with Swagger UI at
`/api/schema/swagger-ui/` and Redoc at `/api/schema/redoc/`. It is generated by
drf-spectacular from the live code, which makes it a useful cross-check against
this file.

## Authentication

**There is none.** Every endpoint below is `AllowAny`. There are no customer
accounts, no registration, no login, no tokens, no cookies, and no
`Authorization` header to send.

The backend has `djangorestframework-simplejwt` configured, and Phase 2 will add
customer accounts. Nothing issues a token today. Do not build a login flow against
it; there is nothing to log into.

Two things stand in for authentication:

- **`access_token`** — a UUID on every order. Possession of it is the entire
  authorization story for reading that order. It is a bearer credential that
  travels in a URL path.
- **`order_number` + `email`** — the throttled fallback for a customer who lost
  the token.

Staff authenticate to Django's admin with a session. There are no staff API
endpoints.

## Pagination

`LimitOffsetPagination`, globally, `default_limit = 25`, `max_limit = 100`.

```json
{
  "count": 42,
  "next": "http://localhost:8000/api/v1/products/?limit=25&offset=25",
  "previous": null,
  "results": []
}
```

`next` and `previous` are absolute URLs or `null`. They are built from the
request's own host, so a server-side call and a browser call receive different
hosts in them. Do not follow them blindly from the other side; recompute
`limit`/`offset` instead.

**`GET /api/v1/categories/` is the exception** and returns a bare array with no
envelope. See below.

There is no cursor pagination.

## Error envelope

Every failure on every endpoint, including a 500, uses one shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Enter a valid email address.",
    "details": { "email": ["Enter a valid email address."] }
  }
}
```

`details` is always an object, `{}` when there is nothing structured to say.

**`code` is the contract.** The backend pins every code in an explicit map rather
than reading DRF's internal `default_code`, precisely so a library upgrade cannot
rename one. `message` is written for humans and may be reworded at any time —
branch on `code`, never on `message`, and never on the status code alone.

| Condition | Status | `code` |
| --- | --- | --- |
| Body was not valid JSON | 400 | `parse_error` |
| Field or serializer validation failed | 400 | `validation_error` |
| Missing or invalid credentials | 401 | `authentication_failed` |
| Authenticated but not permitted | 403 | `permission_denied` |
| Absent, or present but not visible to the caller | 404 | `not_found` |
| Method not routed on this path | 405 | `method_not_allowed` |
| No representation matching `Accept` | 406 | `not_acceptable` |
| Write conflicted with a database constraint | 409 | `conflict` |
| `Content-Type` not supported | 415 | `unsupported_media_type` |
| A business rule rejected the request | 422 | the domain code, below |
| Rate limited | 429 | `throttled` |
| Anything unhandled | 500 | `server_error` |
| Any other DRF exception | as raised | `error` |

The 401 and 403 rows cannot occur in Phase 1: nothing authenticates, so nothing can
fail to. They are listed because the envelope publishes them, not because the
storefront will see them.

### Domain codes (422)

| Code | Raised by | `details` |
| --- | --- | --- |
| `variant_unavailable` | checkout | `{"variant_ids": ["<uuid>", ...]}` — **a list, plural key** |
| `insufficient_stock` | checkout | `{"variant_id": "<uuid>", "requested": 3}` |
| `payment_gateway_unavailable` | checkout | `{"order_number": "TL-2026-000142"}` |
| `payment_not_completed` | Khalti return | `{}` |
| `payment_amount_mismatch` | Khalti return | `{}` |
| `payment_already_processed` | admin actions only | `{}` |
| `invalid_status_transition` | admin actions only | `{}` |
| `order_already_shipped` | admin actions only | `{}` |
| `order_not_cancellable` | admin actions only | `{}` |
| `empty_cart` | unreachable over HTTP | `{}` |

The last five reach no storefront call path. `empty_cart` is unreachable because
the checkout serializer rejects an empty `items` list as a 400 first; the other
four are raised by services the merchant's admin calls, not by any endpoint.

**`insufficient_stock` does not report the available quantity, and this is
deliberate.** Checkout is public, so an error carrying the remaining count would
let one request per variant enumerate the entire inventory — exactly the
disclosure the catalogue endpoints refuse to make. The storefront knows *which*
line failed and nothing more.

### Request id

Every response carries `X-Request-ID`. The backend echoes an inbound one when it
matches `[A-Za-z0-9._-]{1,64}` and generates one otherwise, and every server log
line carries it. Surface it wherever a customer might report a failure.

## Money

Every amount is a **decimal string** with two places: `"4500.00"`. The database
column is a `DecimalField(max_digits=10, decimal_places=2)`.

The currency is **NPR** and is implicit — no amount is ever accompanied by a
currency field. There is no `Money` object on either side.

Khalti's own API speaks integer paisa, but that conversion lives entirely inside
the backend's gateway client. **No paisa value ever crosses this API.**

## Catalogue

### `GET /api/v1/products/`

Public. Paginated. Throttle scope `catalog`, default **600/hour per IP**.

Query parameters:

| Parameter | Value | Notes |
| --- | --- | --- |
| `category` | category slug | Exact match. **Does not descend into children** |
| `size` | size slug | Joins variants |
| `color` | colour slug | Joins variants |
| `min_price` | number | Against `base_price`, not the resolved variant price |
| `max_price` | number | Against `base_price` |
| `in_stock` | boolean | True when *any* variant has stock |
| `search` | string | Case-insensitive substring over `name` and `description` |
| `ordering` | `name`, `base_price`, `created_at` | Prefix `-` to reverse. Nothing else is accepted |
| `limit`, `offset` | integers | `limit` caps at 100 |

`ordering` accepts **only those three fields**. Asking for anything else is
silently ignored rather than rejected, so a typo produces the default order with no
error.

```json
{
  "count": 42,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": "9f0c2e4a-...",
      "name": "Linen Shirt",
      "slug": "linen-shirt",
      "base_price": "4500.00",
      "category": { "name": "Shirts", "slug": "shirts" },
      "primary_image": { "url": "https://res.cloudinary.com/...", "alt_text": "..." },
      "in_stock": true
    }
  ]
}
```

`primary_image` is `null` when the product has no images at all. When the merchant
never ticked "primary", the backend falls back to the first image by sort order, so
a card is never imageless for that reason alone.

### `GET /api/v1/products/{slug}/`

Public. Lookup is by **slug**, not by id. Slugs are unique and SEO-stable, and are
the only detail lookup in the whole API that is not a UUID.

Everything from the list item, plus:

```json
{
  "description": "...",
  "images": [{ "url": "https://res.cloudinary.com/...", "alt_text": "..." }],
  "variants": [
    {
      "id": "1b7d...",
      "size": { "name": "M", "slug": "m" },
      "color": { "name": "Black", "slug": "black" },
      "price": "4500.00",
      "in_stock": true
    }
  ]
}
```

`images` is ordered by the merchant's sort order. `variants` is ordered by size
sort order.

`variant.price` is the **resolved** price: the variant's override if it has one,
otherwise the product's `base_price`. It can therefore differ from `base_price` on
the same payload, and the variant's figure is the one the customer pays.

`size.slug` and `color.slug` are exactly the values `?size=` and `?color=` take, so
a rendered picker already holds what it must send back.

`variant.id` is the only identifier checkout accepts.

**`stock_quantity` is never serialised anywhere.** The API publishes a boolean
`in_stock` on the product and on each variant, and nothing more. There is no way to
show "only 2 left"; do not try to derive it.

A slug that is unknown, and a slug that exists but is unpublished, return the
**same** 404 with the same body. The API does not confirm that a hidden product
exists.

Only `GET` is routed. Any other verb is 405 `method_not_allowed`.

### `GET /api/v1/categories/`

Public. Throttle scope `catalog`.

**A bare array. No pagination envelope.** This is the only endpoint in the API
that answers with a top-level array, and a client written against the product
list's envelope will not read it unchanged.

```json
[
  { "name": "Shirts", "slug": "shirts", "children": [{ "name": "Linen", "slug": "linen" }] },
  { "name": "Trousers", "slug": "trousers", "children": [] }
]
```

Root categories only, each with its immediate children. The tree is exactly **one
level deep** — a child never has a `children` key.

The nesting is presentational only. Filtering the product list by a parent's slug
returns products attached directly to that parent and **not** products in its
children. A navigation menu that implies otherwise will show an empty category.

## Checkout

### `POST /api/v1/checkout/`

Public. Throttle scope `checkout`, default **30/hour per IP**. Returns 201.

```json
{
  "items": [{ "variant_id": "1b7d...", "quantity": 1 }],
  "email": "customer@example.com",
  "phone": "98XXXXXXXX",
  "full_name": "...",
  "address_line": "...",
  "city": "...",
  "district": "...",
  "note": "",
  "payment_method": "khalti"
}
```

| Field | Rule |
| --- | --- |
| `items` | non-empty; an empty list is a 400, not a domain error |
| `items[].variant_id` | UUID of a **variant**, never of a product |
| `items[].quantity` | integer, minimum 1 |
| `email` | valid email |
| `phone` | string, max 32 |
| `full_name` | string, max 200 |
| `address_line` | string, max 255 |
| `city` | string, max 100 |
| `district` | string, max 100, free text |
| `note` | string, max 1000, optional, defaults to `""` |
| `payment_method` | `"cod"` or `"khalti"` |

**No price field is accepted.** Sending `unit_price`, `subtotal` or `total` is not
an error; the fields are ignored and the server's own figures are used. Prices and
availability are re-resolved from the database inside a row lock at placement.

**`district` is free text and decides the shipping fee.** Anything other than
`kathmandu`, `lalitpur` or `bhaktapur` — matched case-insensitively — is charged the
outside-valley rate. A misspelled valley district is overcharged with no error, so
the storefront should offer a fixed list rather than a text input.

Response:

```json
{
  "order_number": "TL-2026-000142",
  "status": "pending",
  "subtotal": "4500.00",
  "shipping_fee": "150.00",
  "total": "4650.00",
  "payment_url": "https://test-pay.khalti.com/?pidx=..."
}
```

`payment_url` is present **only** when `payment_method` is `khalti`. A cash-on-
delivery response **omits the key entirely** rather than sending `null`.

**`access_token` is not in this response, and there is no way to obtain it from
checkout.** It reaches the customer by **confirmation email**, which the backend
sends from inside `place_order` for both payment methods, linking to
`{STOREFRONT_URL}/orders/{access_token}`.

The order's `status` is `pending` regardless of payment method. Stock is already
decremented at this point, before any payment.

Errors:

| Status | Code | When |
| --- | --- | --- |
| 400 | `validation_error` | malformed body, empty cart, `quantity` below 1, unknown `payment_method` |
| 422 | `variant_unavailable` | a variant id is unknown or its product is unpublished |
| 422 | `insufficient_stock` | a line exceeds available stock |
| 422 | `payment_gateway_unavailable` | Khalti could not be reached; **the order was still placed** |
| 429 | `throttled` | over 30/hour from this IP |

**A failed checkout is all or nothing** — no partial order is ever created, and no
stock moves. The one exception is `payment_gateway_unavailable`, where the order
exists, holds stock, and is named in `details.order_number`. There is no
retry-payment endpoint: the customer must place a new order or pay cash on
delivery.

## Orders

### `GET /api/v1/orders/{access_token}/`

Public. `access_token` is a UUID path segment and **is** the credential.

This endpoint declares no throttle scope, so it falls to the global anonymous rate
of **60/hour per IP** — much lower than the catalogue's.

```json
{
  "order_number": "TL-2026-000142",
  "status": "shipped",
  "placed_at": "2026-09-20T10:14:00Z",
  "email": "customer@example.com",
  "phone": "98XXXXXXXX",
  "shipping": {
    "full_name": "...",
    "address_line": "...",
    "city": "...",
    "district": "..."
  },
  "items": [
    {
      "product_name": "Linen Shirt",
      "variant_size": "M",
      "variant_color": "Black",
      "sku": "LIN-SHT-M-BLK",
      "quantity": 1,
      "unit_price": "4500.00"
    }
  ],
  "subtotal": "4500.00",
  "shipping_fee": "150.00",
  "total": "4650.00",
  "payment_method": "khalti"
}
```

`status` is one of `pending`, `paid`, `shipped`, `delivered`, `cancelled`.
`pending` means placed and awaiting payment, and it holds stock.

`payment_method` is `cod` or `khalti`.

Line items carry **snapshots**, not references: `product_name`, `variant_size`,
`variant_color` and `sku` are text copied at purchase time, and `unit_price` is the
price then. They do not change when the catalogue does, and there is no variant id
to link back to a product page.

`access_token` is **never** echoed in the body.

A wrong or unknown token returns 404, never 403.

### `POST /api/v1/orders/lookup/`

Public. Throttle scope `order_lookup`, default **20/hour per IP** — the lowest rate
in the system, because order numbers run in sequence and are therefore guessable.

```json
{ "order_number": "TL-2026-000142", "email": "customer@example.com" }
```

The email is matched case-insensitively. The response is identical in shape to the
order detail endpoint.

**A wrong email and a non-existent order return the same 404, byte for byte.** This
is deliberate — a distinguishable response would confirm which email placed which
order. The storefront must not phrase its error as "that email does not match".

`GET` is not routed here; the route is registered before the token route so that
`orders/lookup/` cannot be read as a UUID.

### Order numbers

Format `TL-<year>-<6 digits>`, e.g. `TL-2026-000142`, from a Postgres sequence.

The sequence is global and does not reset in January, so the year is a label rather
than a counter. **Gaps are normal** — a failed placement burns its number. Do not
infer anything from the digits.

## The Khalti payment return

The storefront never calls Khalti. It does exactly two things: it sends the browser
to `payment_url`, and it serves the two routes Khalti's return redirects to.

```text
storefront            POST /api/v1/checkout/          →  { payment_url }
browser               location = payment_url          →  Khalti hosted page
customer pays on Khalti's domain
Khalti                redirect                        →  backend /api/v1/payments/khalti/return/?pidx=...
backend               server-to-server lookup, then 302
                        success  →  {storefront}/orders/{access_token}
                        failure  →  {storefront}/orders/failed?reason=<code>
```

**This is a contract between the two repositories, and nothing in the backend
enforces it.** Both routes must exist on the storefront or a customer who has
already paid lands on a 404.

`reason` is a domain error code, so the storefront branches on the same vocabulary
as every other call. The values it can carry are `payment_not_completed`,
`payment_amount_mismatch` and `payment_gateway_unavailable`.

The redirect base is the backend's `STOREFRONT_URL` setting, which is also what
confirmation emails link to. If the storefront's
origin changes, that setting changes with it.

Facts about Khalti's own hosted page that affect storefront copy:

- **Only `Completed` is success.** `Pending`, `Initiated`, `Expired`,
  `User canceled`, `Refunded` and `Partially Refunded` all leave the order unpaid.
- **A payment link expires 60 minutes after initiation.** An abandoned tab returned
  to the next morning fails.
- **There is no webhook.** A customer who pays and closes the tab before the
  redirect leaves an order the system believes is unpaid, and nothing detects it.
- The sandbox is **wallet only** — no cards, no e-banking — and sandbox and live use
  different hosts and different keys.
- Live accounts carry an initial **NPR 200 per-transaction ceiling** until KYC is
  completed, which most orders exceed.
- The return round trip includes a synchronous server-to-server call to Khalti, so
  the redirect back to the storefront is **not instant**. The landing route must
  tolerate arriving mid-verification and should not look broken while it loads.

The backend reads **only `pidx`** from Khalti's redirect and distrusts every other
query parameter. The storefront should distrust them too: nothing on a URL returning
from a payment is evidence of anything.

## Throttle rates

All per IP. Every one is **required** in the backend's environment — it has no
defaults, by its own ADR 0008 — so these are the values its `.env.example` ships
rather than fallbacks the code would use:

| Scope | Default | Applies to |
| --- | --- | --- |
| `catalog` | 600/hour | products list, product detail, categories |
| `anon` | 60/hour | order detail by access token, and anything with no scope of its own |
| `checkout` | 30/hour | `POST /checkout/` |
| `order_lookup` | 20/hour | `POST /orders/lookup/` |
| `payment_return` | 60/hour | the backend's own return endpoint |

The catalogue scope is counted **separately** from `anon`, so browsing does not
spend the budget that protects the order lookup.

Exceeding a rate returns 429 with code `throttled`. Throttling still applies when
the backend's Redis is unavailable — it degrades to per-process counting rather
than letting requests through — so the effective limit can be *higher* than the
number above, never lower.

**These are per IP, which is why the storefront does not render customer-scoped
calls on the server.** See [ADR 0001](../decisions/0001-the-browser-makes-every-customer-scoped-call.md).

## CORS

The backend runs `django-cors-headers` with `CORS_ALLOWED_ORIGINS` from an
environment variable and `CORS_ALLOW_CREDENTIALS = True`.

Its local settings already default the allowed origins to `http://localhost:3000`
and `http://127.0.0.1:3000`, so browser calls work in development with no backend
change. **A deployed storefront origin must be added to the backend's
`DJANGO_CORS_ALLOWED_ORIGINS` before its first browser call**, and that is a
backend deploy, not a storefront one.

No credentials are sent on any call — there is nothing to send — so the
credentials flag is irrelevant to the storefront today.

## Images

Product images are Cloudinary delivery URLs, served from `res.cloudinary.com`, and
arrive as a plain `url` string with an `alt_text` beside it.

- **In production they are absolute Cloudinary URLs. In local development they
  are relative paths** like `/media/products/tee.jpg`, because the backend's
  local settings override its storage backend to the filesystem. The storefront
  resolves a relative one against the API base in `lib/api`; handed to
  `next/image` unresolved it would point at the storefront's own origin.
- They are **public and permanent**. Unpublishing a product hides it from the API
  but does nothing to its images.
- The API applies **no transformations** and gives no dimensions, aspect ratio or
  blur placeholder. Whatever the merchant uploaded is what is served, at full size.
- `alt_text` can be an empty string when the merchant left it blank.

The host must be declared in `next.config.ts` under `images.remotePatterns` before
`next/image` will load one.

## Health

```text
GET /health/        liveness; touches nothing; {"status": "ok"}
GET /health/ready/  readiness; checks database and cache; 200 or 503
```

Unversioned, outside `/api/v1/`. Useful for a local "is the backend up" check and
for nothing else the storefront needs. `/health/` is also what the external
keep-alive monitor calls to stop Render's free tier putting the backend to sleep.
It is set up outside this repository; see the README, "Keep the backend awake".

## Not offered by this API

Everything here is absent by decision, not by oversight. Do not build a
client-side workaround for one without raising it against the backend repository
first.

- **No cart.** There is no cart table and no cart endpoint. The cart is entirely
  the storefront's problem, and the API sees it once, as the `items` array in a
  checkout request.
- **No customer accounts**, no login, no order history, no saved addresses, no
  "reorder". Every purchase is standalone.
- **No guarantee that a confirmation email arrived.** The backend now sends one,
  but `send_email` catches everything and never raises, so a failed send does not
  fail the order and nothing tells the storefront. A customer who mistyped their
  address has the order number and the lookup, and nothing else.
- **No stock counts.** Only the `in_stock` boolean, and no available quantity in
  the `insufficient_stock` error.
- **No child-category filtering.** `?category=` matches one category exactly.
- **No cursor pagination**, only limit/offset.
- **No discounts, coupons, gift cards, sale prices, or tax.** `base_price` is the
  only price concept, and `shipping_fee` the only addition to it.
- **No product reviews, ratings, related products, or recommendations.**
- **No wishlist, no restock notification, no abandoned-cart anything.**
- **No fuzzy search.** `?search=` is a case-insensitive substring match over name
  and description, so "tshirt" does not find "t-shirt". No ranking, no stemming, no
  typo tolerance.
- **No faceted counts.** The API will not say how many products match a filter
  before it is applied.
- **No maximum cart size** is enforced on checkout. The storefront should impose a
  sane one anyway.
- **No refunds** and no cancellation endpoint. Both are merchant actions performed
  outside the API.
- **No write access to the catalogue.** Products, sizes and colours are
  admin-only.
- **No multi-currency.** NPR is implicit everywhere.
